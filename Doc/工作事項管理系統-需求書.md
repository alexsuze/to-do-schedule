## 1. 專案概述

### 1.1 目的
建置一套「工作事項管理系統」，讓使用者能夠記錄、追蹤與管理日常工作事項，並透過看板、時程表、列表三種檢視模式掌握工作進度，同時在事項到期前以 Email 主動提醒。

### 1.2 範圍
本期功能包含：

1. 工作事項的基本管理（新增、編輯、刪除、復原）
2. 多看板管理與看板模式（類似 Trello）
3. 檢視模式切換（看板 / 時程表 / 列表）
4. Email 到期通知（透過 Resend 寄送）

本期不包含（待後續版本討論）：

- 帳號登入、多人協作與權限控管
- 行動裝置原生 App
- 第三方行事曆同步（Google Calendar、Outlook）
- 時程表模式的拖曳調整日期
- 事項間的相依關係（前置任務連線）

### 1.3 名詞定義

| 名詞 | 說明 |
|------|------|
| 工作事項（Task） | 系統中最小的管理單位，代表一件待辦的工作 |
| 看板（Board） | 一組工作事項的容器，可依專案或主題建立多個看板 |
| 欄位（Column） | 看板中的一個狀態分類，例如「待辦」、「進行中」、「完成」 |
| 卡片（Card） | 看板模式中代表單一工作事項的視覺元件 |
| 時程表（Timeline） | 以時間軸呈現工作事項起訖區間的檢視方式，類似甘特圖 |
| 列表（List View） | 以表格逐列呈現工作事項的檢視方式 |
| 回收桶（Trash） | 存放已刪除事項的區域，可從中復原 |

## 2. 使用者與存取方式

- 本期為**單一使用者**系統，**不需登入**。
- 開啟前端網址即可直接使用所有功能。
- 資料模型不設 User 實體，通知設定等全域偏好以單一「設定」文件儲存。
- 因後端 API 無登入保護，且前端部署於公開的 GitHub Pages，後端採簡易 API Token（前端於 `X-API-Token` Header 帶入、後端由環境變數比對）防止未授權存取。詳見 5.4。

## 3. 功能需求

### 3.1 工作事項基本管理

#### 3.1.1 工作事項欄位

| 欄位 | 型別 | 必填 | 說明 |
|------|------|------|------|
| 所屬看板 | 參照 | 是 | 每個事項必屬於一個看板 |
| 標題 | 文字（≤ 100 字） | 是 | 工作事項名稱 |
| 描述 | 長文字 | 否 | 詳細說明，支援多行 |
| 狀態 | 參照欄位 | 是 | 對應所屬看板的欄位，預設為第一個欄位 |
| 優先度 | 列舉 | 否 | 高 / 中 / 低，預設「中」 |
| 開始日期 | 日期 | 否 | 時程表模式起點 |
| 到期日期 | 日期時間 | 否 | 時程表模式終點，亦為 Email 通知依據 |
| 標籤 | 多選文字 | 否 | 自訂分類標籤，可多個 |
| 通知覆寫 | 物件 | 否 | 該事項專屬的通知設定，見 3.5.2 |
| 建立時間 | 日期時間 | 系統 | 自動產生 |
| 更新時間 | 日期時間 | 系統 | 自動更新 |
| 完成時間 | 日期時間 | 系統 | 移入「完成」類型欄位時自動填入 |
| 刪除時間 | 日期時間 | 系統 | 軟刪除標記，見 3.1.4 |

#### 3.1.2 新增工作事項
- 使用者可在看板模式與列表模式下新增工作事項；時程表模式為唯讀，不提供新增。
- 必填欄位僅有「標題」，其餘欄位可事後補充。
- 新增後預設落在目前看板的第一個欄位。
- 若未填開始日期而有到期日期，時程表以到期日期當日呈現為單日事項。

#### 3.1.3 編輯工作事項
- 點擊事項可開啟編輯視窗（Modal 或側邊面板），修改所有可編輯欄位。
- **日期的調整只能透過看板模式的卡片編輯視窗進行**；時程表模式僅顯示、不可修改。
- 列表模式可行內修改狀態、優先度與完成勾選，其他欄位需開啟編輯視窗。
- 儲存後即時反映在所有檢視模式。
- 修改到期日期時，應同步重新計算 Email 通知排程。

#### 3.1.4 刪除工作事項
- 刪除前需二次確認，避免誤刪。
- 採**軟刪除**：標記 `deleted_at`，事項自所有檢視模式中消失，移入回收桶。
- 刪除後應同時取消該事項尚未寄出的通知。
- 回收桶內的事項保留 **30 天**，逾期由後端排程自動永久刪除。

#### 3.1.5 復原已刪除事項
- 提供「回收桶」頁面，列出目前看板（或全部看板）已刪除但未逾 30 天的事項，顯示標題、原欄位、刪除時間、剩餘天數。
- 點擊「復原」即清除 `deleted_at`，事項回到原欄位；若原欄位已被刪除，則回到看板第一個欄位。
- 復原後若事項仍有未來的到期日期且未完成，重新建立通知排程。
- 提供「永久刪除」與「清空回收桶」，需二次確認。

#### 3.1.6 驗證規則
- 標題不可為空白。
- 到期日期不可早於開始日期。
- 到期時間若設定於過去，系統應提示但允許儲存。

### 3.2 多看板管理

#### 3.2.1 看板欄位

| 欄位 | 說明 |
|------|------|
| 名稱 | 必填，≤ 50 字 |
| 顏色 / 圖示 | 選填，用於側邊欄辨識 |
| 排序值 | 側邊欄顯示順序 |
| 最後檢視模式 | kanban / timeline / list |

#### 3.2.2 看板操作
- 側邊欄列出所有看板，點擊即切換；系統記住最後開啟的看板，下次進入時預設顯示。
- 可新增、重新命名、變更顏色、拖曳排序、刪除看板。
- 新建看板時自動建立預設三個欄位：「待辦」、「進行中」、「完成」。
- 刪除看板時需二次確認，看板內所有事項一併軟刪除並可自回收桶復原（復原事項時若看板已刪除，需先復原看板）。
- 至少需保留一個看板；系統首次啟動時自動建立名為「我的工作」的預設看板。

#### 3.2.3 事項移動
- 編輯視窗提供「移至其他看板」功能，選擇目標看板與目標欄位後移動。

---

### 3.3 看板模式（Kanban）

#### 3.3.1 欄位管理
- 每個看板擁有各自獨立的欄位。
- 使用者可新增、重新命名、刪除、拖曳排序欄位。
- 每個欄位可標記「完成類型」，事項移入此類欄位時自動填入完成時間並取消通知；移出時清除完成時間並重新排程通知。預設「完成」欄位為完成類型。
- 刪除欄位時，若欄位內仍有卡片，需讓使用者選擇「一併刪除（軟刪除）」或「移至其他欄位」。
- 至少需保留一個欄位。

#### 3.3.2 卡片操作
- **拖曳移動**：卡片可在同一欄位內上下拖曳排序，或拖曳至其他欄位以變更狀態。
- **快速新增**：每個欄位底部提供「+ 新增卡片」，輸入標題即可建立。
- **卡片摘要**：卡片顯示標題、優先度顏色標記、到期日期、標籤。
- **到期提示**：到期日期在 24 小時內以警示色顯示；已逾期以紅色顯示；已完成則灰階。
- 點擊卡片開啟編輯視窗（同 3.1.3）。

#### 3.3.3 排序與篩選
- 卡片在欄位內依使用者拖曳順序排列，系統需儲存排序值。
- 提供依「優先度」、「到期日期」、「標籤」篩選，篩選條件在切換檢視模式時保留。

---

### 3.4 檢視模式切換

#### 3.4.1 通用需求
- 頁面上方提供模式切換元件（Tab 或 Segmented Control）：看板 / 時程表 / 列表。
- 三種模式操作的是**目前選取看板**的同一份事項資料，任一模式的變更即時反映到其他模式。
- 每個看板各自記住最後使用的模式。
- 篩選條件跨模式共用。

#### 3.4.2 看板模式
詳見 3.3。

#### 3.4.3 時程表模式（類似甘特圖，本期唯讀）
- **時間軸**：橫軸為時間，可切換「日 / 週 / 月」尺度；縱軸為工作事項，每列一項。
- **事項長條**：依開始日期與到期日期繪製長條，長條顏色依狀態或優先度區分。
- **今日標線**：以垂直線標示今日位置，並預設將視窗捲動至今日。
- **唯讀**：本期不支援拖曳長條或調整兩端日期。點擊長條可開啟編輯視窗（同 3.1.3），日期修改於該視窗完成。
- **無日期事項**：未設定任何日期的事項集中列於下方「未排程」區塊。
- 本期不需支援事項間的相依關係。

#### 3.4.4 列表模式
- 以表格呈現，欄位包含：完成勾選框、標題、狀態、優先度、開始日期、到期日期、標籤。
- 可點擊表頭依任一欄位排序（升冪 / 降冪）。
- 可直接在列表上勾選完成、變更狀態與優先度（行內編輯）。
- 提供關鍵字搜尋（比對標題與描述）。
- 支援分組顯示：依狀態、優先度或到期日（今天 / 本週 / 之後 / 逾期 / 無日期）分組。
- 提供「+ 新增事項」按鈕。

### 3.5 Email 通知功能

#### 3.5.1 通知設定（全域）
使用者可在「設定」頁面設定：

| 設定項目 | 說明 | 預設值 |
|----------|------|--------|
| 啟用 Email 通知 | 總開關 | 開啟 |
| 收件 Email | 通知寄送地址 | 空白，需使用者填寫 |
| 預設提前時間 | 到期前多久寄送，可複選 | 1 天前 |
| 提前時間選項 | 到期時、15 分鐘前、1 小時前、1 天前、3 天前、1 週前 | — |
| 每日摘要 | 每日固定時間寄送當日到期 / 逾期事項彙整（跨看板） | 關閉 |
| 每日摘要時間 | 摘要寄送時間 | 09:00 |
| 時區 | 到期時間與通知時間依此時區計算 | Asia/Taipei |

- 設定頁提供「寄送測試信」按鈕，驗證 Resend 設定與收件地址是否正確。

#### 3.5.2 單一事項通知設定
- 編輯事項時可覆寫全域設定，為該事項指定專屬提前時間（可複選）。
- 可針對單一事項關閉通知。

#### 3.5.3 通知觸發規則
- 只對「有到期日期」且「不在完成類型欄位」且「未刪除」的事項排程通知。
- 事項到期日期變更時，重新計算所有尚未寄出的通知時間。
- 事項移入完成類型欄位、刪除或所屬看板刪除時，取消尚未寄出的通知。
- 同一事項同一提前時間只寄送一次，避免重複。
- 若排程時間已過（例如後端停機期間），恢復後對逾時未寄出且事項仍未到期者立即補寄；已到期者併入每日摘要的逾期提醒。

#### 3.5.4 Email 內容
- 寄件者：本期無自有網域，使用 Resend 提供的測試寄件者 `onboarding@resend.dev`。
- 限制：未驗證網域時，Resend 只允許寄送至註冊 Resend 帳號所使用的 Email，因此「收件 Email」設定需填該地址。日後若取得網域並完成 DNS 驗證，僅需更換 `RESEND_FROM_EMAIL` 環境變數。
- 主旨格式：`[工作提醒] {標題} 將於 {到期日期時間} 到期`
- 內文包含：看板名稱、標題、描述摘要、狀態、優先度、到期日期時間、開啟事項的連結（前端網址 + 看板與事項 ID）。
- 每日摘要主旨：`[每日摘要] {日期} 今日到期 {N} 項、逾期 {M} 項`
- Email 需同時提供 HTML 與純文字版本。

#### 3.5.5 通知紀錄
- 系統記錄每封通知的排程時間、寄送時間、對象事項、Resend 回傳的訊息 ID、寄送結果（成功 / 失敗）。
- 寄送失敗時重試最多 3 次，間隔 5 分鐘；全數失敗則記錄錯誤訊息供排查。
- 設定頁提供最近 50 筆通知紀錄的檢視。

## 4. 非功能需求

| 類別 | 需求 |
|------|------|
| 效能 | 單一看板在 500 筆事項以內應於 1 秒內完成載入與模式切換 |
| 相容性 | 支援桌面瀏覽器（Chrome、Edge、Firefox、Safari 最新兩版）；行動裝置瀏覽器可正常瀏覽，拖曳功能為次要 |
| 資料保存 | 資料持久化於 MongoDB，非僅存於瀏覽器 |
| 安全性 | Resend API Key、MongoDB 連線字串、API Token 不得寫入程式碼，需由環境變數管理 |
| 時區 | 到期時間以 UTC 儲存，依設定時區顯示與計算通知時間 |
| 可維護性 | 檢視模式應以共用資料層（Pinia store）為基礎，新增模式不需修改資料模型 |
| 可用性 | 後端停機期間前端應顯示明確錯誤訊息，並於恢復後自動重新載入 |

## 5. 技術架構

### 5.1 總覽

```
┌──────────────────────────┐        HTTPS / JSON        ┌──────────────────────────┐
│  前端（GitHub Pages）      │ ─────────────────────────▶ │  後端（Railway）           │
│  Vue 3 + Pinia + Quasar   │ ◀───────────────────────── │  Java REST API            │
└──────────────────────────┘                             │  + 通知排程器              │
                                                         └─────────┬────────────────┘
                                                                   │
                                                  ┌────────────────┼────────────────┐
                                                  ▼                                 ▼
                                        ┌──────────────────┐             ┌──────────────────┐
                                        │     MongoDB       │             │   Resend API      │
                                        └──────────────────┘             └──────────────────┘
```

### 5.2 前端
- **技術**：Vue 3（Composition API）+ Pinia（狀態管理）+ Quasar（UI 元件與拖曳、日期元件）。
- **部署**：GitHub Pages，透過 GitHub Actions 於 push 至 `main` 時自動建置與部署。
- **路由**：使用 hash 模式或設定正確的 `publicPath`，避免 GitHub Pages 子路徑導致重新整理 404。
- **設定**：後端 API 網址與 API Token 由建置時環境變數（GitHub Secrets）注入。
- **狀態管理**：Pinia store 分為 `boards`、`tasks`、`settings`、`ui`（目前看板、檢視模式、篩選條件），三種檢視模式皆讀取同一 `tasks` store。

### 5.3 後端
- **技術**：Java 21 + Spring Boot 4.1 REST API（Spring Initializr 已不再提供 3.x，故採 4.x）。
- **部署**：Railway，連結 GitHub repo 於 push 至 `main` 時自動部署。
- **通知排程器**：後端內建排程（例如每分鐘掃描一次 `notifications` 中 `status = pending` 且 `scheduled_at <= now` 的紀錄並寄送），另每日執行回收桶清理與每日摘要。
- **Email**：透過 Resend REST API 寄送，API Key 由 Railway 環境變數提供。
- **資料庫**：MongoDB Atlas 免費層（M0），連線字串由 Railway 環境變數提供。
- **CORS**：僅允許 GitHub Pages 的前端網域。

### 5.4 環境變數

| 變數 | 位置 | 說明 |
|------|------|------|
| `MONGODB_URI` | Railway | MongoDB Atlas 連線字串 |
| `RESEND_API_KEY` | Railway | Resend API Key |
| `RESEND_FROM_EMAIL` | Railway | 寄件者地址，本期為 `onboarding@resend.dev` |
| `API_TOKEN` | Railway | 前後端共用的簡易存取 Token |
| `CORS_ALLOWED_ORIGIN` | Railway | 前端網址 |
| `VITE_API_BASE_URL` | GitHub Secrets | 後端 API 網址 |
| `VITE_API_TOKEN` | GitHub Secrets | 與後端 `API_TOKEN` 相同 |

> 注意：前端為靜態網站，`VITE_API_TOKEN` 會被打包進前端程式碼，任何取得網址的人皆可讀取。此機制僅能阻擋隨機掃描，無法作為真正的身分驗證。若需更高安全性，未來應導入登入機制。

## 6. 資料模型（MongoDB Collections）

```
settings（單一文件）
  - _id
  - notify_email
  - notifications_enabled
  - default_lead_times      # 例：["1d"]；可用值 "0m","15m","1h","1d","3d","1w"
  - daily_digest_enabled
  - daily_digest_time       # "09:00"
  - timezone                # "Asia/Taipei"
  - last_board_id

boards
  - _id
  - name
  - color
  - order
  - last_view_mode          # kanban | timeline | list
  - columns: [              # 內嵌，每個看板的欄位數量少
      { _id, name, order, is_done_type }
    ]
  - deleted_at
  - created_at
  - updated_at

tasks
  - _id
  - board_id
  - column_id
  - title
  - description
  - priority                # high | medium | low
  - start_date              # date
  - due_at                  # datetime (UTC)
  - order                   # 欄位內排序
  - tags: [string]
  - notification_override   # null | { enabled, lead_times }
  - completed_at
  - deleted_at              # 軟刪除，含索引供回收桶清理
  - created_at
  - updated_at

notifications
  - _id
  - task_id
  - type                    # reminder | daily_digest
  - lead_time               # "1d" 等；daily_digest 為 null
  - scheduled_at
  - sent_at
  - status                  # pending | sent | failed | cancelled
  - retry_count
  - resend_message_id
  - error_message
```

**建議索引**
- `tasks`: `{ board_id, deleted_at }`、`{ due_at }`、`{ deleted_at }`
- `notifications`: `{ status, scheduled_at }`、`{ task_id }`
